# Triage of an externally-proposed "Working Style" instruction block

An external conversation argued that a bare "KISS" instruction is unusable
because "simple" is relative, and proposed replacing it with a longer
operationalized Working Style block: seven Simplicity bullets, four Accuracy
bullets, an Output section, and a Decisions section.

The premise is correct and worth stating in the project's own terms. An
instruction whose compliance and violation look identical from the transcript is
prose, not a check. That is the same defect class this project keeps finding in
its own validators, expressed in text: a rule that cannot fire reads exactly like
one that passed.

The proposed cure is only half right. The useful axis is falsifiability, not
verbosity, and Rule 26 plus its three enforcement sites already carry a stricter
version of the falsifiable half. `adversary.md` already bars a shape finding
unless the reviewer can name the mechanism at `file:line`, the locked requirement
it does not serve, and the simpler change that meets the same requirement —
"This feels over-built" names none of the three and is downgraded to MINOR. Rule
26 additionally carries three mechanisms the proposal has no equivalent of: the
(c) contract forcing every new guard to declare its own removal condition, the
(e) scope fence stopping "simple" from becoming licence to skip a step, and (d)
simplification as a first-class finding.

Adopting the block wholesale would therefore have built a parallel path beside a
proven one with no rationale record — a Rule 26(b) violation on its face. Two
parts were absorbed; the rest is recorded here as rejected so the same proposal
does not return as a fresh idea.

## Absorbed

**The one-call-site counter, into Rule 26(a).** 26(a) banned mechanism added "for
requirements that do not exist", which is a judgement about a requirement's
existence with no counting test. The proposal's "no abstraction until a second
concrete use case exists" is arithmetic over the diff. It now sits in 26(a) with
26(b) as its escape hatch, which is what bounds its false positives.

**Two triggers, into Rule 26(b).** 26(b) fired on exactly one condition, a
parallel path beside a proven one. The proposal's dependency rule and measurement
rule have the same shape as 26(b) itself — each fires on the absence of a stated
sentence rather than on a judgement — so they became additional 26(b) triggers
rather than new rules, reusing the same artifacts (ADR at design time,
`DECIDED_AUTONOMOUSLY` at implementation time) and the same enforcement.

Both enforcement sites had the 26(b) record enumerated *bound to parallel paths*.
Widening SKILL.md alone would have produced triggers no reviewer is told to look
for. `adversary.md` and `code-reviewer.md` (both the checklist entry and the
Over-Engineering severity rule) were widened in the same change.

## Rejected

**"Prefer the smallest change that solves the stated problem."** This is KISS
restated, and it survived its own critique — the proposal opened by rejecting
exactly this construction. Not falsifiable, no enforcer possible.

**"If the request implies more machinery than the problem requires, say so."**
Relocates the relativity to the trigger rather than removing it. Fires never or
always. `adversary.md`'s name-all-three bar exists specifically to keep findings
of this shape out of the stream.

**"Edit existing files before creating new ones."** Already present, with a fence
it lacks: `v0.12.0-resident-context-slimming-spec.md` routes to existing
seam-owners first and allows new files where no owner exists. The unfenced form
is a regression, and it is cheap to comply with badly by cramming content into
the wrong file.

**The Accuracy section.** Largely covered. Evidence cells and gate machinery
cover "do not state that code works without running it"; Rule 21 covers
recall-versus-read for rule files. One clause is genuinely uncovered — do not
fill a codebase gap from general knowledge — but it has no enforcer today, and by
Rule 26(c) a mechanism that cannot state what catches it is not added. It remains
a candidate, not a change.

**The Output and Decisions sections.** Out of scope. `rule-authoring.md` governs
rule prose, Rule 13 and Rule 12 carry the architecture-versus-implementation
decision split, and chat output style is operator preference rather than pipeline
machinery.

## Where it did not go

`templates/coding-conventions.md.template` was the intuitive home and is the
wrong one. It is an install-time scaffold: written once by `install.sh`,
protected thereafter by `ai-dlc-protect.sh`, and absent from `core-manifest.md`.
Edits there reach new installs only and never reach an existing consumer. Core is
the only destination that propagates.
