# v0.28.0 — Gate-Metrics Emission (structured, decisive ai-dlc measurement)

Status: **proposed + drafted** (stacked on v0.27.0 #61). Makes forward ai-dlc
runs emit machine-readable per-check outcome records so consumer history yields
**decisive** efficacy/cost data instead of prose archaeology.

## Problem (proven by the v0.27.0 audit)

The v0.27.0 machinery-efficacy audit had to reverse-engineer "did check X ever
catch anything" from three prose sources — gate-log `**Remediations:**` footers,
escalation-archive `Check N` mentions, and 284 retro narratives — and it
**confounded** because:

1. **Verdicts are prose, not data.** Gate-log per-check lines are
   `- Check N (title): PASSED — <free text>`. 706 parsed verdicts gave 0 FAILED
   (catches hide in prose footers). Efficacy is not machine-countable.
2. **Two catalogs, one number space.** The flagship consumer layers a domain
   catalog via `extensions/checks/` that redefines shared numbers (its "Check 20"
   ≠ distribution Check 20) and adds 19b/23–33. `Check N` in consumer logs cannot
   be attributed to a distribution check by number.

Net: no decisive answer to "which checks earn their token cost," and no trend
data (catch-rate per check per sprint, defect-class mix, cost vs catch).

## Design (Rule 26 minimum mechanism)

**One structured record per check per gate, appended where the prose entry is
already written (Check 12). No new check, no new script, no new infra.** The
same per-check verdict data Check 12 already assembles for the prose log is
*also* written as one JSONL line — near-free, and the prose log is unchanged
(it stays the human/audit trail; JSONL is the metrics trail).

### File
`_bmad-output/implementation-artifacts/gate-metrics.jsonl` — append-only,
one JSON object per line, machine-read only (never loaded verbatim into the
lead's context; read via context-mode/`ctx_execute`). Rotates with the gate-log
epoch (Rule 25(c)): closed epochs move to `gate-metrics-archive-<epoch>.jsonl`.

### Record schema (`GATE_METRIC v1`)
```json
{
  "v": 1,
  "sprint": 277,
  "gate": "implementation",
  "phase": "implementation→sprint-review",
  "ts": "2026-06-30T14:20:05Z",
  "sha": "abc1234",
  "catalog": "core",
  "check": "17",
  "title": "skill-invocation provenance",
  "verdict": "PASS",
  "defect_class": null,
  "evidence": "docs/reviews/sprint-277-...md",
  "tok_slice": 7569
}
```

| field | meaning | why it kills the confound |
|-------|---------|---------------------------|
| `catalog` | `core` (this distribution) or `extension:<extension-file-id>` (a consumer domain check, from its `extensions/checks/*.md` frontmatter `id`) | **the drift-fix** — consumer C25 emits `extension:gate-validation-domain`, distribution Check 20 emits `core`; never conflated again |
| `check` | check id string within that catalog | number is namespaced by `catalog`, so reuse is unambiguous |
| `verdict` | `PASS` \| `FAIL` \| `NA` \| `DEFERRED` | machine-countable efficacy — no prose parse |
| `defect_class` | on FAIL/remediation: short taxonomy token (`missing-provenance`, `orphaned-fn`, `stub-unbacked`, `intensity-under-run`, …); else `null` | catch-counting BY CLASS is exact; feeds "what does this check actually catch" |
| `evidence` | path / run-id pointer, never prose | keeps the record small + reproducible |
| `tok_slice` | tokens of the loaded check slice (**required as of v0.28.1**) | the COST side of efficacy = cost ÷ catch, per check, over time; `∞` when catches=0 is the dormancy signal |

### Emission point
Check 12 gains an emission clause: after the prose entry + post-write
verification, append one `GATE_METRIC v1` line per **validation** check
evaluated this gate. A distribution check emits `catalog:"core"`; a consumer
extension check emits `catalog:"extension:<id>"` (the extension author sets it —
Rule 27 layering).

**Tightening (v0.28.1), from the first live emission (graph S286):**
- **Validation checks only.** The procedural gate-mechanics checks 12–15
  (log-append / announce / snapshot / verify-snapshot) are bookkeeping, never
  defect-catchers, and are NOT emitted (emitting the emitter is circular). Every
  other manifest-loaded check IS emitted, including `NA` (an `NA` exposure is
  signal — the check ran and self-skipped).
- **`tok_slice` is required** (was optional). Without it, cost-vs-catch is not
  computable — the whole point. The reader flags records missing it.

### Reader
`scripts/audit-machinery-efficacy.js` prefers `gate-metrics.jsonl` when present
(decisive, namespaced) and falls back to prose parsing for pre-v0.28.0 sprints.
A follow-on can point context-mode's `ctx_insight` dashboard at the same file
for per-check catch-rate / cost trends — out of scope here (KISS).

## What this makes decisive going forward
- **Efficacy per check** = `count(verdict=FAIL by real defect_class) / count(gate exposures)`, exact, per catalog — no prose, no confound.
- **Cost vs catch** = `tok_slice` totals ÷ catches → the actual "does this check earn its tokens" number the v0.27.0 audit could only estimate.
- **Defect-class mix** — what the pipeline actually catches over time.
- **Dormancy** — a `core` check with N exposures and 0 real-defect FAILs across a window is a *sound* hold candidate (unlike the v0.27.0 prose signal).

## Non-goals (KISS)
- No metrics service / DB — a JSONL append is the mechanism.
- No dashboard in this change — the file is dashboard-ready; wiring is optional follow-on.
- Prose gate-log stays; this is additive, not a replacement.

## Rollout
- Distribution: Check 12 emission clause + schema note in `gate-validation.md`;
  audit-script reader; this spec. MINOR (additive gate output; existing consumers
  keep working — absence of the file just means the reader uses the prose path).
- Consumers pick it up on next `/ai-dlc`; the file starts accumulating from the
  first gate after upgrade. Historical sprints stay prose-only (reader handles both).
- Verify: emit a sample record at a real gate, re-run the audit reader against a
  mixed (JSONL + prose) tree, confirm GATE_MANIFEST resolve + H1 harness stay green.
