# v0.25.0 Proposal — Lead-Inline Delegation Closeout (§0 backfill + fix-directly purge)

Status: **Proposed, unimplemented.** Target version: 0.25.0. Continues the
delegation arc that Rule 28 opened
([[v0.8.0-planning-subagent-offload-spec]] established Rule 24; Rule 28
generalized it to "delegation is the default, inline is the exception").

This proposal does not add a rule. Rule 28 already mandates everything here.
It closes the gap between the **rule** and the **step-file procedures** that
predate it — the places where a step still instructs the lead to read, draft,
edit, or patch inline in violation of the rule already on the books. Two
independent levers, shippable separately:

- **Lever 1 — §0 backfill.** Four read/write-heavy steps lack the
  exploration-dispatch `§0` block that discovery / research-requirements /
  carry-over-evaluation / the three analysis steps already carry. Their
  reads and edits therefore default to the lead. Add the dispatch.
- **Lever 2 — fix-directly purge.** Four step procedures carry a bare
  "fix directly" / "apply fixes" / "update it directly" imperative that puts
  the lead's own hands on source or story files. Requalify each to name the
  dispatch target.

## 1. Problem (measured against Rule 28 + Rule 24)

Rule 28 non-delegable set = **(a) orchestration, (b) routing, (c)
gate-validation decisions**. Everything else — reading code to understand it,
drafting an artifact, applying a fix, editing source — is a delegable action
and, done inline, is a lead-conduct retro finding *by the skill's own rule*.

Rule 24's `§0` exploration-dispatch block is the concrete mechanism that
discharges the read-heavy half of that mandate. Audit of the §0 presence
across the planning/analysis steps:

| Step | §0 dispatch present | Read/write-heavy work on lead |
|---|:--:|---|
| discovery | ✅ | — (except §1a grep, see §1.5) |
| research-requirements | ✅ | — |
| carry-over-evaluation | ✅ | — (except §4a cross-check, see §1.5) |
| deep-codebase-analysis | ✅ | — |
| codebase-inventory | ✅ | — |
| doc-reconciliation | ✅ | — |
| **architecture** | ❌ | AS-IS-from-code reading, existing-arch assessment |
| **ui-direction** | ❌ | entire generative mockup step |
| **stories-test-strategy** | ❌ | framework-import grep sweep |
| **doc-repair-backfill** | ❌ | read-heavy + write-heavy doc repair |

The four unmarked steps are the Lever 1 targets. Rule 24's own
"Offloaded steps" enumeration does not list any of them — so the rule text
and the step files are mutually consistent in the *wrong* direction: both
omit the dispatch. Lever 1 fixes both sides.

Separately, four procedures carry an inline-patch imperative (Lever 2):

| Site | Current text | Delegable action done inline |
|---|---|---|
| `deploy-validate.md:203` | "For any drift: **fix directly**, redeploy, re-verify" | lead edits UI source |
| `deploy-validate.md:274` | "If human requests fixes: **Apply fixes**, redeploy, re-validate" | lead patches code post-PVC |
| `sprint-review.md:81` | §2 party mode "**Apply all improvements**" (unqualified) | reads as lead applying code changes |
| `sprint-review-next.md:42` | "If any story needs modification, **update it directly**" | lead edits story ACs |

In all four, the surrounding orchestration verbs (redeploy, re-validate,
re-present checkpoint, mark `skipped` in sprint-status) are legitimately
lead-owned (Rule 28a). Only the **source/story edit** is misplaced.

## 2. Lever 1 — §0 backfill

Two dispatch shapes, by the nature of the work being offloaded.

### 2.1 Shape A — analyst exploration §0 (Rule 24 extension)

Byte-identical in structure to the existing discovery/carry-over §0. Applies
where the offloaded work is **reading** (codebase, docs) that produces a
context digest the lead then authors/decides against.

**architecture.md** — insert before `### 1. Context Loading`:

```
### 0. Exploration dispatch (Rule 24)

If `planning_offload: on` (default) AND the variant reads existing code or
architecture (feature, brownfield-a, brownfield-c — NOT greenfield /
brownfield-b, which author from scratch via `/bmad-create-architecture`),
do NOT read the codebase or existing architecture inline. Spawn an `analyst`
subagent (Agent tool, bound to `.claude/team-roles/analyst.md` per SKILL.md
Rule 19 — both bindings: `model` and the standing role-contract Read line)
scoped to the AS-IS / existing-architecture read — it reads the code and the
current architecture doc and writes a context digest to
`_bmad-output/planning-artifacts/architecture-context.md`, returning only
`{artifact_path, summary, gaps}`. Then resume at section 1. **Sections 1
onward stay inline in the lead** — the PRD/brief read, all design decisions,
ADR authoring, and the Rule 8 validation cycle are never offloaded. If
`planning_offload: off`, run all sections inline. Per SKILL.md Rule 24.
```

Consequence for §2: the brownfield-a "Document the AS-IS architecture from
code" and the feature "Assess whether existing architecture supports this
feature as-is" clauses now consume the analyst's digest rather than reading
the codebase inline; the design verdict and ADR authoring stay lead/architect.

**HPE disconfirmation-probe (§2, L57–59) — narrow companion fix.** The clause
"the lead executes the `disconfirmation_probe` against production, records the
result" runs a **read-only** probe before dev dispatch. Reword to: the probe
execution is dispatched (analyst for a log/query probe, qa for a test probe);
the lead owns recording the result against `disconfirmation_threshold` and the
GO/NO-GO-for-dispatch decision. This is gate-evidence *collection* (delegable),
not the gate *decision* (28c, lead). Lower confidence than the §0 add — ship
only if it does not complicate the probe's evidence-attachment audit.

**doc-repair-backfill.md** — the §1 repair is write-heavy, not read-heavy
(the read was already done by `doc-reconciliation` upstream). Replace §1's
inline edits with a dispatch:

```
### 1. Repair Existing Docs

Read `_bmad-output/planning-artifacts/doc-reconciliation.md` (the finding
set only — small). For every STALE/WRONG/MISSING-FROM-DOCS finding, dispatch
a `dev` teammate (Agent tool, role-bound per Rule 19) to apply the edits:
update each document to match the codebase, preserve accurate content, add a
correction log, add docs for undocumented code, and flag MISSING-FROM-CODE
with `[NOT IMPLEMENTED]` (never remove). If any target document is a
protected path, dispatch `protected-path-editor` for that file instead
(Rule 28 / `implementation.md`). The lead validates the returned edits
against the finding set; it does not apply them inline.
```

§2 backfill (creation sub-skills), §3 validation cycle, §4 gate stay inline —
consistent with every other creation step. The lead reads the reconciliation
*finding set* (small, bounded) to validate the dev's edits; it never re-reads
the full stale documents.

**stories-test-strategy.md pre-flight (a)** — the framework-import grep
sweep (L144–148) is the only clearly-delegable read in this step. Fold it
into a scoped analyst probe rather than a full §0 (the rest of the step —
`/bmad-create-epics-and-stories`, dispatch-plan authoring — is legitimately
inline). Reword (a):

```
**(a) Framework-import inspection.** For every test framework prescribed in
story ACs, the framework's presence in the codebase MUST be verified before
the AC is written. Dispatch an `analyst` (role-bound per Rule 19) to grep for
each framework's import/config and return a `{framework: present|absent}`
map; the lead consumes the map when authoring/fixing ACs. Absent framework =
AC unimplementable as written → fix the AC or add a setup story.
```

Pre-flight (b) role/step-file existence check stays lead: it is
dispatch-plan orchestration prep (Rule 28a).

### 2.2 Shape B — ux delegation §0 (Rule 28, generative work)

**ui-direction.md** is not an *exploration* step — it *produces* design
artifacts (wireframes, copy, CSS-class specs, accessibility review). That is
production work owned by the **ux** role, not analyst reading. It gets a §0
that dispatches ux, not analyst:

```
### 0. Design dispatch (Rule 28)

UI mockup generation, copy, CSS-class specification, and the accessibility /
device review are design production, not orchestration/routing/gate — so per
Rule 28 they are delegated. Spawn a `ux` subagent (Agent tool, bound to
`.claude/team-roles/ux.md` per Rule 19 — `model` + role-contract Read line)
scoped to sections 1, 2, and 4: it generates the ASCII wireframes and copy
for each new UI surface, confirms each introduced CSS class against the
stylesheet, runs the accessibility/device check, writes the result to
`_bmad-output/planning-artifacts/ui-mockups-sprint-N.md`, and returns only
`{artifact_path, summary, decisions}`. The lead resumes at section 3
(present) and section 5 (proceed). **Sections 3 and 5 stay inline** — reading
the artifact, presenting it non-blocking to the human, and routing to
implementation are lead actions. An absent artifact at the returned path is
non-delivery; the lead re-dispatches (Rule 24 delivery discipline).
```

`ui.md` role file already exists (46 lines) — this is the first step that
routes to it, closing an unused-role gap.

### 2.3 Rule 24 reconciliation (SKILL.md)

Update Rule 24's "Offloaded steps" enumeration to match:

- Add `architecture` and `stories-test-strategy` (framework-import probe) to
  the **split-offload** list (exploration only; authoring + validation inline).
- Add `doc-repair-backfill` — special-cased: §1 repair is a **dev/
  protected-path-editor** write-dispatch, not an analyst read-dispatch (call
  it out explicitly so the rule and the step agree on the role).
- `ui-direction` is delegated under Rule 28 to **ux**, not Rule 24 to analyst —
  add `ux` to Rule 28's "Everything else is delegated" role enumeration
  (currently dev / analyst / protected-path-editor / code-reviewer / qa;
  ux is implied by "everything else" but naming it removes the ambiguity that
  let ui-direction stay solo).

## 3. Lever 2 — fix-directly purge

Surgical requalification. Each edit keeps the orchestration verbs on the lead
and moves only the source/story edit to a teammate.

**deploy-validate.md:203** —
> For any drift: fix directly, redeploy, re-verify

becomes

> For any drift: dispatch a `dev` teammate (role-bound per Rule 19) to correct
> the UI source; the lead then redeploys and re-verifies. Redeploy and
> re-verification are deploy-gate orchestration (Rule 28a) and stay on the lead.

**deploy-validate.md:274** —
> If **human requests fixes:** Apply fixes, redeploy, re-validate, and present
> the checkpoint again.

becomes

> If **human requests fixes:** dispatch `dev` for the fixes, `code-reviewer`
> to re-review the changed files, and `qa` to re-validate affected stories;
> the lead then redeploys, re-validates the deploy gate, and presents the
> checkpoint again. Only the code edit is delegated — the redeploy and the
> checkpoint re-presentation stay on the lead.

**sprint-review.md:81** — §2 party mode's unqualified "Apply all improvements"
inherits §1's and §3's discipline ("Dev teammates apply code fixes"). Append
the same qualifier:

> - Apply all improvements. **Code changes are applied by dev teammates, not
>   inline by the lead (Rule 28); the lead owns disposition, not the edit.**

**sprint-review-next.md:42** (lowest confidence — story-relevance modification
sits close to planning orchestration) —
> If any story needs modification, update it directly.

becomes

> If any story needs modification, the modification is authored through the
> §3 validation cycle (SM/dev via the story sub-skills), not edited inline by
> the lead. Marking a story `skipped` in sprint-status.yaml with a rationale
> is orchestration bookkeeping and stays on the lead.

## 4. Enforcement (Rule 26(c) — audit before adding mechanism)

No new gate check and no new detector. Two existing mechanisms already cover
these violations at retro:

1. **Rule 28's own "lead-conduct retro finding"** — an inline action outside
   the non-delegable set is already a retro finding. The §0 blocks and the
   requalified imperatives simply make the *correct* path the default the lead
   reads, so the finding fires only on genuine regression.
2. **`retro.md` Step 4 rule-file audit** — extend its scope note to check that
   every step with read/write-heavy work carries the §0 dispatch (a
   relocation-pointer-style structural invariant, not a new script). A step
   that regrows inline reads without a §0 is flagged there.

This matches the discipline Rule 28 states about itself ("Build no detector
for this — the lead's read of the expected path is the check"). Adding a gate
script here would be exactly the speculative machinery Rule 26 forbids.

**Minimum-mechanism contract for this proposal.** Failure caught: a step
procedure that predates Rule 28 keeping delegable read/draft/edit/patch work
inline, so the lead saturates its own context and collapses the
production/orchestration boundary — the action-heavy-misread and
token-saturation failure modes the rules exist to prevent, regrown at the
step-file layer where the rule text never reached. False-positive cost: an
occasional dispatch of work the lead could have done in one turn (the same
cost Rule 24 and Rule 28 already accept). Removal condition: retire the §0
scaffolding once the harness structurally prevents the lead from taking
non-orchestration actions (same condition as Rule 28 itself).

## 5. Rollout

Both levers are text-only edits to core step files + one SKILL.md rule
reconciliation. No hook, no script, no CI change. Ship order:

1. **Lever 2 first** — smallest, highest-signal, zero new structure. Four
   line edits. Validate against a live sprint's deploy-validate + sprint-review.
2. **Lever 1 Shape A** — architecture + doc-repair-backfill + stories probe
   §0 blocks. Replicates the proven discovery/carry-over pattern.
3. **Lever 1 Shape B** — ui-direction ux dispatch. Exercises the ux role for
   the first time; validate the mockup artifact round-trips through the ux
   subagent before relying on the non-blocking present.
4. **Rule 24 / Rule 28 reconciliation** (SKILL.md) — lands with Lever 1 so the
   rule text and the step files agree in the same version.

Each core-file edit routes through the layered-rulebook discipline (Rule 27):
these are core-owned files, edited upstream, distributed by `/ai-dlc-update`.

## 6. Out of scope

- **retro.md inline reads** (Tier 3 of the audit — Step 1 context load, Step 4
  rule-file audit, Step 7b next-sprint assembly). Real, but retro's own
  analyst-dispatch is a heavier design change (retro is 740 lines and its
  read-heavy sections interleave with lead-owned decisions). Deferred to a
  follow-on spec.
- **discovery §1a grep sweep** and **carry-over-evaluation §4a incident-log
  cross-check** — both land just past their existing §0 scope. Widening those
  two §0 blocks is a one-line scope extension each; fold into Lever 1 Shape A
  if convenient, but they are minor.
- Any new gate check or CI detector (Rule 26 — enforcement rides existing
  retro audits).
