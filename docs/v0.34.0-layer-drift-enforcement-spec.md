# v0.34.0 — Layer-drift enforcement (Rule 27 gets teeth)

Status: **IMPLEMENTED** in v0.34.0 (this doc is the design record).
Descendant of the Phase-2 layer split (Rule 27) and the consumer-sync arc.

## 1. Problem (measured on the real consumer, ~/git/graph @ v0.33.1)

Rule 27's three-layer model (core / extensions / overrides) is what keeps `core`
byte-reconcilable with upstream. Its safety depends on **drift detection**: when
upstream changes a core rule that a consumer layer shadows or hooks, the consumer
must be told. A full sweep of graph's 12 overrides + 27 extensions found that
drift detection **is not working, and never was**:

| defect | evidence |
|---|---|
| **No script implements the layered reconcile.** `reconcile/preclassify.sh` has zero references to `extensions`/`overrides`/`base_sha`/`shadows`/`hooks`. The "Layered consumers" reconcile is prose in `ai-dlc-update/SKILL.md` — an instruction to an agent to remember to run `git diff` per override. | grep |
| **5 of 12 `base_sha` values are CONSUMER commits, not distribution commits.** Three are literally the consumer's own `chore(ai-dlc-update): reconcile distribution X → Y` merge commits. `git diff <base_sha>..theirs` in the distribution returns `fatal: bad revision`; the skill defines no handling → silent skip. | `7bf089d1`, `2f82aa2a`, `862e9e9c`, `04781db3`, `0ed7bbb` all resolve in graph, none in ai-dlc |
| **Extensions have no drift anchor at all.** The entry contract carries `hooks: <file>` only — no `base_sha`, no section id. Nothing can detect that core changed underneath an extension. | `extensions/README.md` |
| **Absorption has no retirement step.** The push-candidate flow drains extensions into a push ledger and upstream absorbs them into core — but nothing tells the consumer "this is in core now; delete your copy." Every successful absorption leaves a landmine. | `discovery-domain.md` §1a duplicates *and* contradicts core §1a, which upstream absorbed |

**Live consequences found in graph** (all silent):
- `steps__retro__domain-sections.md` (29 KB, `base_sha` = a graph commit) shadows
  core §4a. v0.33.0 added a `docs/architecture.md` 60k threshold to the §4a
  artifact-size audit; v0.33.2 routed gate-log to rotation. **Both are discarded.**
  Graph will never warn on architecture-doc size. The drift check that should have
  flagged this cannot run.
- `retro-push.md` defines a second live `### 5c` colliding with the override's
  `### 5c`, and refers 5× to a `Step 5d` that no layer defines.
- `SKILL-push.md` instructs rotating the gate-log inside the retro PR; the
  retro-side extension and the override both forbid exactly that (doing it trips
  guarded-merge Check 4 `SECTION_MISSING` → merge denied).
- `discovery-domain.md` asserts `pending.md` "holds only OPEN items"; core says the
  opposite, explicitly.
- `roles/qa-domain.md` restates core's QA Context Loading verbatim, pre-slice —
  the read-list loads twice, once without the Rule 25(b) slice mandate.

## 2. Key enabling property (makes the authoring-time check free)

A **correct** `base_sha` is a distribution sha: it resolves in the distribution
repo and **not** in the consumer repo. A **poisoned** one resolves in the consumer
repo. Verified across all 9 base_shas in graph — perfect mutual exclusivity, 9/9.

Therefore a consumer-side linter can catch base_sha poisoning with **no
distribution checkout**: `git rev-parse --verify <sha>^{commit}` succeeding in the
consumer repo is, by itself, proof the value is wrong.

## 3. Design — two scripts, split by what each may legally see

`ai-dlc-update` carries a HARD CONSTRAINT: self-contained, reads only its own
files, `git`, and the stamp — never the pipeline rulebook. Layer *frontmatter* is
data it already classifies; layer *authoring policy* is a pipeline concern. Hence
the split.

### A. `core/skills/ai-dlc-update/reconcile/layer-drift.sh` (pull-time)

`layer-drift.sh <dist-repo> <base-sha> <theirs-ref> <consumer-root>` → TSV
`STATUS<TAB>ENTRY<TAB>TARGET<TAB>DETAIL`. Deterministic; shells to git only.
Mechanizes what was prose. Statuses:

- `OVERRIDE-BASE-CONSUMER-SHA` — base_sha resolves in the consumer repo. **HARD.**
- `OVERRIDE-BASE-UNRESOLVABLE` — resolves nowhere. **HARD.**
- `OVERRIDE-DRIFT-SECTION` — the shadowed section's text changed `base..theirs`.
- `OVERRIDE-ANCHOR-UNRESOLVED` — anchor not locatable in `theirs` (upstream
  restructured). Conservative: surface for operator, never guess.
- `OVERRIDE-OK`
- `EXTENSION-HOOK-MISSING` — `hooks:` target absent in `theirs`.
- `EXTENSION-HOOK-DRIFT` — the hooked core file changed `base..theirs` (file-grain;
  extensions have no finer anchor).
- `EXTENSION-RETIRE-CANDIDATE` — a section the extension defines now also exists in
  `theirs`' hooked core file. **This is the absorption-retirement signal.**
- `EXTENSION-OK`

Fixes 1, 2, 3. Wired as `ai-dlc-update` step 3c; its output populates two new
dry-run report sections (**layer-drift list**, **retirement list**), and any HARD
status blocks `apply` until the operator adjudicates.

### B. `core/scripts/validate-layer-entries.sh` (authoring-time, consumer-side)

`validate-layer-entries.sh [project-root]`. No distribution needed. ERROR → exit 1.

1. Overrides: `shadows:` + `base_sha:` present; base_sha is 7–40 hex; **ERROR if it
   resolves in the consumer repo** (§2).
2. Extensions: `kind:`, `hooks:`, `id:` present; `hooks:` target exists (path-mapped).
3. **Duplicate section text** — an extension heading identical to a heading in its
   hooked core file → the extension restates core (retire it, or file as override).
4. **Duplicate section number** — two live definitions of the same step number for
   one target across core + extensions + rendered overrides. Catches the dual `§5c`
   that identical-text matching misses (the titles differ).
5. **Dangling step reference** — a `Step <n>` / `§<n>` reference resolving to no
   section defined by any layer for that target. Collects both `### <n>.` headings
   **and** `**<n>. …**` bold anchors (the override defines `7a-post` that way; a
   heading-only scan would false-positive it). Catches `Step 5d`.
6. **Restricting language in an additive layer** (WARN) — `Only … are valid`,
   `is NOT subject`, closed enumerations. An extension that *restricts* core is a
   mis-filed override. This is the `artifact-consolidation-push.md` shape.

Fix 4. Wired into `rule-authoring.md` (authoring-time routing) and `retro.md`
Close-Out Sweep (periodic sweep, alongside the artifact-size audit).

## 4. Rule 27 amendments (`SKILL.md`)

- **`base_sha` provenance (normative).** It MUST be a *distribution* sha. A value
  that resolves in the consumer repo is invalid — the reconcile treats it as a
  hard finding, not a skip.
- **Retirement duty on absorption.** When upstream lands a layer entry's content
  in core, the consumer MUST retire that entry. `EXTENSION-RETIRE-CANDIDATE` is the
  signal; retirement is an operator-gated delete (upstream never writes the layer).
- **Additive means additive.** An extension MUST NOT restate or restrict a core
  section. Restating forks the prose and rots; restricting is an override wearing
  extension frontmatter.

## 5. Minimum mechanism (Rule 26(c))

- **Catches:** a consumer layer silently shadowing/duplicating/contradicting a core
  rule that upstream has since changed — proven live 5× in graph, including two of
  this distribution's own shipped changes being discarded unseen.
- **False-positive cost:** one operator re-confirmation per genuinely-still-valid
  override whose core section moved; one WARN per deliberate restriction.
- **Removal condition:** retire when core ships as an immutable package with
  machine-checked layer bindings (ids resolved at load), making prose-anchored
  drift impossible.

## 6. Verification

Both scripts are validated against graph's real layer set (12 overrides, 27
extensions), whose ground truth was established by an independent adversarial
sweep: expect exactly 5 `OVERRIDE-BASE-CONSUMER-SHA`, the `retro-push.md` dual-§5c
and `Step 5d` findings, the `discovery-domain.md` duplicate §1a, and
`qa-domain.md`'s duplicate `## Validation Checklist` — and NO finding for
`Step 5e` / `Step 7a-post`, which resolve in the rendered pipeline (the
false-positive control).
