# v0.100.0 spec — the missing grain for an additive rule that belongs to a core section

Status: **proposed**. Deferred from the v0.96.0–v0.98.0 push-candidate batch.

## The reported defect, and why it is filed against the wrong component

The graph consumer reports that `layer-drift.sh`'s `EXTENSION-RESTATES-CORE` matches on
section number + title, so it "cannot distinguish *added to core §N* from *copied core
§N*." Three of its five flags were an additive `extensions/` entry that hooks a core
section by reusing its heading — "the natural way to write one" — and it proposes
comparing body overlap, or giving extensions a declared `adds-to:` grain.

The described behavior is real. `same_section()` (`layer-drift.sh:220`) compares heading
text only, and the emit sites at 397 and 428 fire on a number+title match.

But it is not a defect in `layer-drift.sh`. That tool is enforcing a documented contract,
stated in `extensions/README.md` and quoted in the tool's own message as Rule 27(c):

> **Never restate a core section.** Same heading, or the same step number with the same
> title, means the rendered file defines it twice and a "Step 5c" reference becomes
> ambiguous. An extension's body is *added* to core, not merged with it.

The reason is about the **heading**, not the body. Extensions render into one merged file;
two sections with one heading make a bare "Step 5c" reference in a gate log unresolvable.
That is the same failure the catalog-labelling rule (Rule 27(d)) exists to prevent, and it
has already happened once — the README records a lead disambiguating by hand in prose.

So body-overlap comparison is the wrong remedy: it would silence a warning whose stated
purpose the consumer's entries genuinely trip, and it would let a *reworded* duplicate
through, which is the case `same_section`'s stoplist-and-containment scoring exists to
catch. **Recommend not touching the matcher.**

## The real gap

The consumer is not wrong that it is stuck. Its entries add a rule that genuinely belongs
to a core section, and the layer system offers only two grains, neither of which fits:

- **`extensions/`** — additive, but must not reuse the core heading. An entry with a
  distinct heading is legal but detached: the rule renders somewhere else in the file,
  away from the core section it qualifies.
- **`overrides/`** — may target a core section (`shadows: <file>#<id>`), but the body
  *replaces* the shadowed rule. To keep core's content and add one clause, the consumer
  must reproduce the entire core section verbatim, and then carry `base_sha` drift
  maintenance on prose it never meant to change.

That is the consumer's actual complaint, correctly stated: *"the only way to silence them
was to refile as `overrides/`, which forces the entry to reproduce the whole core section
verbatim just to keep it."* Confirmed against the overrides contract.

So there is no grain for **"append to core §N"** — the most natural thing a consumer
extending a rulebook wants to do. Both existing grains are reasonable; the set is
incomplete.

## The decision

### Option A — add an `appends_to:` grain (recommended)

An extension entry may declare:

```markdown
---
kind: check | step-domain | role
hooks: steps/sprint-review.md
appends_to: steps/sprint-review.md#3          # the core section this qualifies
id: <stable-id>
---
```

Semantics: the body renders **inside** the named core section, after core's own content,
under core's heading — so the entry carries no heading of its own and the "two sections,
one number" ambiguity cannot arise. `layer-drift.sh` skips `EXTENSION-RESTATES-CORE` for
an entry whose `appends_to:` resolves, because such an entry is declaring the relationship
the tool would otherwise be guessing at.

What must be settled before building:

1. **Does it need a `base_sha`?** An override carries one because it replaces core and must
   notice when core changes underneath. An append is additive, so the argument is weaker —
   but an append to a section that upstream *deletes* is orphaned, and an append that
   duplicates a clause core later grows is a duplicate nobody flags. Leaning yes, on the
   evidence that the un-anchored case is exactly how the v0.13.0 duplicate hid for ~35
   pulls.
2. **Anchor resolution.** `shadows:` already uses `<file>#<id>`, and `reconcile/lib.sh`'s
   `section_of()` is the single-homed resolver (I21). Reuse it; do not grow a second.
3. **Render order** with multiple appends to one section, and interaction with `overrides/`
   shadowing that same section — precedence is currently `overrides > extensions > core`,
   and an append to an overridden section needs a defined answer.
4. **The loader is prose.** Rule 27 describes layer loading in SKILL.md; a new grain has to
   land there, in `extensions/README.md`, in `validate-layer-entries.sh`, and in
   `layer-drift.sh`. Four homes — check whether the grain can be derived in fewer.

Cost: this is the largest of the three options and the only one that removes the
consumer's bind. Item 4 is where it could get expensive; scope it before committing.

### Option B — document the convention, change no code

Declare that an additive rule qualifying a core section uses a **distinct, labelled**
heading (the Rule 27(d) pattern already used for check catalogs), e.g.
`### 3. [ext:sprint-review-domain] Decision-branch execution coverage.` No collision, no
`RESTATES-CORE`, no new grain — the entry is simply legible as an addition rather than
disguised as core's section.

Cost: a README paragraph. Buys: the consumer's three flags go away today, correctly.
Does not buy: the rule still renders as its own section rather than inside the one it
qualifies, which is the ergonomic complaint underneath the report.

**This is the right first move regardless of Option A**, because it is what today's
contract already implies and the consumer evidently did not read it that way. If Option A
ships later, these entries convert cleanly.

### Option C — body-overlap comparison in `layer-drift.sh`

Rejected, as argued above: it weakens a deliberate contract, is blind to reworded
duplicates, and treats a missing-grain problem as a matcher-precision problem.

## Verification

- For Option B: no code change, so the check is that the consumer's three flagged entries
  (`sprint-review-domain` §0/§3, `sprint-review-push` §3) stop being flagged once
  relabelled, and that a genuine duplicate still *is* flagged. Run `layer-drift.sh` against
  the reference consumer before and after — the second half is the one that matters, since
  a change that silences everything is indistinguishable from one that silences the right
  things.
- For Option A: a fixture in the shape of `layer-catalog-collision` / `layer-readopt-gate`
  — an entry with `appends_to:` resolving (no flag), one whose anchor no longer resolves
  upstream (flagged), and one that restates without declaring (still flagged). The third is
  the mutation guard: if declaring `appends_to:` silences a true restatement, the grain has
  become an opt-out from Rule 27(c) rather than a way to satisfy it.
