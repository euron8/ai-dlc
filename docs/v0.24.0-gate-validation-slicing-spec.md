# v0.24.0 Proposal — Gate-Validation Slicing (procedure extraction + gate-type manifest)

Status: **Phase 1 (Lever 1) SHIPPED** — cumulative `gate-validation.md`
13,544 → 10,748 tok (**−2,796 resident every gate, −21%**); see §9. **Lever 2
(gate-type manifest) pending.** Target version: 0.24.0. Continues the
resident-context
arc (v0.5.0–v0.12.0). Prior work slimmed the **orchestrator** (`SKILL.md`,
v0.12.0). This targets the **second-largest always-resident file**:
`core/skills/ai-dlc/steps/gate-validation.md`, referenced (not loaded as a
step) by every pipeline step at every phase transition — so its full body is
resident on every gate of every sprint.

Same philosophy as v0.12.0 ([[v0.12.0-resident-context-slimming-spec]]):
**relocate and conditionally-load, never trim.** No rule text is deleted,
softened, or paraphrased. Every byte survives; it stops occupying the window
during the gates where its seam is not active.

Two independent levers, orderable separately:
- **Lever 1 — procedure extraction.** Move step-file-*invoked* procedures out
  of the resident gate body. Unconditional, universal, zero fidelity-contract
  change. Ship first, alone if nothing else.
- **Lever 2 — gate-type manifest.** Load only the checks applicable to the
  current gate type. Requires re-expressing the Rule 21 "whole file loaded"
  fidelity guarantee as "every *applicable* check loaded", enforced by a
  manifest + the existing H1 harness meta-check.

## 1. Problem (measured on distribution gate-validation.md @ v0.23.0)

`gate-validation.md` = **54.2 KB ≈ 13,480 tok** (chars/4 est, ±15%), 33
sections, resident for the entire duration of every gate. It is 97–100%
prose — near-zero code fences — so the whole file is rule text.

The file is monolithic: it carries **every** check for **every** gate type on
**every** gate, plus three step-file-invoked procedures that are not gate
checks at all. Measured token distribution by bucket:

| Bucket | Tok | Content |
|---|--:|---|
| `U` universal core | 2,649 | checks 1,2,3,4,7,12,13,15, H1, H2, Gate Failure — run every gate |
| `ref` invoked procedures | 3,852 | Check 14 snapshot update (1,626), Auto-handoff eval (1,945), Sub-step snapshot (281) — invoked *by reference* from step files, not gate checks |
| `plan` planning gates | 1,622 | 1c research-invocation, 19 self-reflexive Gate-2 map, 20 validation-intensity |
| `impl` implementation gates | 2,235 | 6, 8, 11, 11a, 16 stub-audit, 18 test-debt, 22 role-binding |
| `retro` retro/close gates | 1,395 | 17 skill-provenance, core-layer immutability |
| `story` story gates | 927 | 3a origin check, 5 status consistency |
| `review` sprint-review gate | 427 | 21 test-strategy deliverable |
| `schema` schema-modifying stories | 219 | 10 schema/API field verification |
| `ui` UI sprint gates | 154 | 9 visual verification |

**Only 2,649 tok (20%) is universal.** The remaining 80% is either a
gate-type-conditional check (already self-labeled "Implementation gates
only", "story gates only", "all planning gates", etc.) or an invoked
procedure — both carried resident on gates where they never fire.

Top pain-point context is unchanged from v0.12.0: the dominant failure mode
is **token saturation** (window exhaustion → compaction churn), not spend.
Cache amortizes the *dollar* cost of resident text; it does not free the
*window*. Fewer resident tokens per gate = more headroom before compaction,
and gates are where the lead's window is already most loaded (artifacts +
snapshot + role context all co-resident).

## 2. The scar-tissue constraint (do not regress)

ai-dlc rule verbosity is deliberate scar tissue — each check patched an
observed gate-bypass. **This spec MUST NOT trim, soften, delete, or
paraphrase any check text.** This is why `caveman-compress` was rejected for
this file: it is a non-deterministic LLM rewrite of exactly the guard prose,
guarded by a validator blind to semantic drift (it checks code fences / URLs
/ headings, not whether a conditional inverted). The 45% it claimed and the
scar-tissue risk are the *same tokens*.

The mechanisms here are **byte-preserving**:
- Lever 1 **moves** three procedure blocks verbatim to a sibling file; a
  one-line pointer stays where each was.
- Lever 2 **conditionally loads** verbatim sections by gate type; nothing is
  edited, only gated behind a manifest.

Every byte still executes, unchanged, on the gates where it applies.

## 3. Design principles

1. **Check identity is stable and addressable.** Every check gets a stable
   anchor ID (`CHECK-1`, `CHECK-3a`, `CHECK-14`, `H1`, …) so the manifest and
   the H1 completeness assertion can name it. IDs already exist informally in
   the headings; formalize them.
2. **Relocate procedures to a seam-owner, gate checks stay in-file.** Lever 1
   moves the three `ref` procedures to a new `steps/_gate-procedures.md` (no
   existing owner; the step files that invoke them are many). Gate *checks*
   never leave `gate-validation.md` — they are conditionally loaded, not
   relocated (they have no single seam-owner; the gate is their seam).
3. **The manifest is the single source of applicability.** One table maps
   gate type → required check IDs. No check self-decides; the loader reads the
   manifest. This keeps the "which checks apply" decision auditable in one
   place instead of scattered across 33 parentheticals.
4. **Fidelity is proven, not assumed.** Rule 21 currently guarantees fidelity
   by loading the whole file + `STEP_LOADED_TOKEN`. Under slicing, H1 (already
   the harness meta-check that enumerates phase-specific checks) is extended
   to assert every manifest-required check for the active gate type is present
   in loaded context. A missing required check is a FAIL, exactly as a skipped
   check is today.
5. **Pointer must not rot.** Each Lever-1 pointer + the manifest gain a
   resolve-check in `retro.md` Step 4 (the pointer-resolve audit added in
   v0.12.0), so a dangling procedure pointer or a manifest ID with no matching
   anchor fails a retro gate.

## 4. Lever 1 — procedure extraction (unconditional, ship first)

Three sections are procedures **invoked by reference** from step files, not
gate checks. The file itself labels two of them "(referenced by step files)".
They run only when a step says "run sub-step snapshot update" / "run
auto-handoff evaluation" / Check 14's snapshot procedure fires — yet all
three sit resident on every gate.

| Est tok | Block | → Target | Pointer left behind |
|--:|---|---|---|
| 1,945 | `Auto-handoff evaluation` (L856–1003) | `steps/_gate-procedures.md` | trigger stays in the resident Check set; procedure body moves |
| 1,626 | `Check 14. Update pipeline snapshot` procedure (L342–471) | `steps/_gate-procedures.md` | Check 14's *mandate* ("snapshot is source of truth; update at every gate") + the snapshot path stay resident; the 6-section update mechanics move |
| 281 | `Sub-step snapshot update` (L831–855) | `steps/_gate-procedures.md` | one-line pointer at the invocation seam |

**Gross: 3,852 tok. Net after ~3 pointer lines: ~3,700 tok removed from every
gate, every type, unconditionally.**

**Invocation audit (open-Q §10.4 resolved — GREEN).** Grepped all step +
role + SKILL files. **Every** call site invokes these three by explicit named
reference — `Run sub-step snapshot update (see gate-validation.md "Sub-step
snapshot update")`, `run auto-handoff evaluation (see gate-validation.md
"Auto-handoff evaluation")` at a named Seam, `gate-validation.md Check 14`.
**No step relies on the procedure body already being resident.** Relocation
is safe. Named-reference call sites found:
- **sub-step snapshot update** — 8 step files (implementation, architecture,
  sprint-review, sprint-review-next, stories-test-strategy, discovery,
  doc-repair-backfill, research-requirements).
- **auto-handoff evaluation** — 10 step files + retro.md + SKILL.md (L387/392).
- **Check 14** — SKILL.md (L59/290/299/363), route.md (L44/273/294),
  retro.md, codebase-inventory.md.

Because the references name the **anchor text**, relocation must repoint them,
or the references dangle. Concrete repoint work (Phase 1):
1. Every `see gate-validation.md "X"` → `see _gate-procedures.md "X"` for the
   three moved anchors (~20 references across ~11 files).
2. **`retro.md` L228 validates the `Check 14` anchor exists on disk** — update
   it to resolve the anchor at its new home (this on-disk check is also the
   guard that *catches* a bad move; it must know the new location).
3. **SKILL.md L59/290/299/363 treat Check 14 as the snapshot field-schema
   owner** ("Check 14 owns the schema"). If the schema moves with the
   procedure, repoint these four lines; if the schema stays resident under the
   Check 14 mandate, leave them. Decide per §10.6.

Design notes:
- Check 14 splits: the **decision** ("update the living snapshot at this
  gate", plus the snapshot file path and the "source of truth" mandate) is
  correctness-resident and stays; only the **procedure** (the 6-section
  structure, refresh order, reminder-threshold mechanics) moves. Same
  trigger-stays/procedure-moves split v0.12.0 §3.1 used for handoff. Note:
  Check 14 has more resident consumers than the other two (SKILL.md calls it
  the schema owner), so its split is the most entangled — see §10.6.
- Auto-handoff evaluation is a full procedure already cross-referenced from
  `SKILL.md` (relocated there in v0.12.0 Phase 2, `42379c5`); this moves the
  *evaluation body* out of the gate resident path to the shared procedure
  file, leaving the "evaluate auto-handoff at safe seams" trigger resident.
- `_gate-procedures.md` gets its own `STEP_LOADED_TOKEN` and is loaded
  `READ AND FOLLOW`-style at the invocation seam, per Rule 21.

Lever 1 needs **no manifest and no H1 change** — the moved blocks are not
gate checks, so the "every check loaded" contract is untouched. This is why
it ships first and independently.

## 5. Lever 2 — gate-type manifest (conditional check loading)

### 5.1 The manifest

A single table at the top of `gate-validation.md` (resident, ~200 tok) maps
gate type → required check IDs. Universal checks are implicit (always
required). Sketch:

```
<!-- GATE_MANIFEST v1 -->
| Gate type          | Required checks (beyond universal core)      |
|--------------------|----------------------------------------------|
| universal (all)    | 1, 2, 3, 4, 7, 12, 13, 15, H1, H2, failure   |
| planning           | 1c, 19, 20                                   |
| story              | 3a, 5                                         |
| implementation     | 6, 8, 11, 11a, 16, 18, 22                     |
| schema-story       | implementation + 10                          |
| ui-sprint          | implementation + 9                           |
| sprint-review      | 21                                           |
| retro/close        | 17, core-layer-immutability                  |
```

The loader (the step invoking gate validation, per Rule 21) reads the
manifest, then loads the universal core + the current gate type's rows.
Result per gate type (universal core 2,649 + conditional, `ref` already gone
via Lever 1):

| Gate | Sliced resident | vs 13,480 full |
|---|--:|--:|
| sprint-review | 3,076 | −77% |
| story | 3,576 | −73% |
| retro | 4,044 | −70% |
| planning | 4,271 | −68% |
| ui-sprint | 5,038 | −63% |
| implementation | 5,103 | −62% |

Combined with Lever 1, the worst case (implementation) drops from 13,480 to
**5,103 tok resident**, and the best case (sprint-review) to **3,076 tok** —
deterministically, without editing one word of any check.

### 5.2 Fidelity re-expression (the load-bearing part)

Rule 21 today: "READ AND FOLLOW = a Read call; the whole file must be loaded;
`STEP_LOADED_TOKEN` proves it." The header states "Every check must PASS. Any
failure blocks the gate." Slicing weakens "whole file loaded" — so the
fidelity guarantee must be re-anchored, or a sliced load could silently skip
a required check (the exact class of failure the scar tissue exists to
prevent).

Re-expression:
1. **Rule 21 amendment.** "Loaded" for `gate-validation.md` means: the
   universal core **and** every check the `GATE_MANIFEST` marks required for
   the declared gate type. The gate must declare its type before loading.
2. **Per-section load tokens.** Each check emits its own anchor comment
   (`<!-- CHECK_LOADED: 3a -->`). The file-level `STEP_LOADED_TOKEN` is no
   longer sufficient proof, because the file is no longer loaded whole.
3. **H1 becomes the completeness prover.** H1 already runs at every gate and
   already enumerates phase-specific checks + asserts each ships a fixture.
   Extend it: H1 reads `GATE_MANIFEST`, resolves the declared gate type, and
   asserts every required check ID is present in loaded context (its
   `CHECK_LOADED` anchor is visible). Missing required check = **FAIL**,
   identical severity to a skipped check today. This turns "did we load
   enough?" into a checked invariant instead of a trust-the-loader
   assumption.
4. **H2 gains a slicing-bypass fixture.** A seeded gate that declares
   `implementation` but loads only the planning slice (omitting Check 6/8/11)
   MUST be caught by H1. Fixture at `tests/fixtures/check-manifest-bypass/`,
   following the H1/H2 fixture convention (README.md + seed.sh, cited by check
   body). This is the adversarial self-test that the fidelity re-expression
   actually holds.

### 5.3 Gate-type declaration

Slicing requires each gate to know its type before loading. The pipeline
already distinguishes gate types implicitly (a planning gate vs an
implementation gate vs retro). Make it explicit: the invoking step passes the
gate type when it says "run gate validation" (e.g. "run gate validation
[implementation]"). `route.md` / the step files already know their phase, so
the type is available at the call site — this is surfacing existing knowledge,
not computing anything new. Open question §10.2 on where the canonical
gate-type enum lives.

## 6. Correctness-resident set — MUST stay (never sliced out)

- **Universal core (2,649 tok)** — checks 1,2,3,4,7,12,13,15, H1, H2, Gate
  Failure. Run every gate regardless of type; always loaded.
- **The manifest itself + Rule 21 amendment** — the loader needs them before
  it can decide what to load.
- **Check 14 mandate + snapshot path** (post Lever-1 split) — the snapshot is
  the post-compact recovery source of truth; its trigger and path stay
  resident even though the update procedure moves.
- **H1 / H2** — the harness that *proves* slicing didn't drop a check. If H1
  itself were sliceable the guarantee would be circular. H1/H2 are universal.

## 7. Risks & mitigations

| Risk | Mitigation |
|---|---|
| Sliced load silently omits a required check (the core scar-tissue failure) | §5.2: H1 reads the manifest and FAILs on any missing required `CHECK_LOADED` anchor; H2 seeds a slicing-bypass fixture that H1 must catch. Fidelity becomes a checked invariant, not a loader assumption. |
| Gate declares wrong type → wrong slice | Type comes from the invoking step's known phase (§5.3), not inferred. A mis-declared type still loads the universal core (which includes H1), and H1's manifest resolution surfaces the mismatch if the loaded checks don't match the declared type. |
| My gate-type classification (§1 table) is wrong for a check | The §1 buckets are a read of the 33 parentheticals; checks 16/18/19 tagging is judgment. **Validate the manifest against the actual pipeline gate-type matrix before shipping Lever 2.** Lever 1's 3,852 tok is robust regardless — those three are procedures under any typing. |
| Manifest drifts from the checks (a new check added, not added to manifest) | H1 enumerates checks *from the file* and cross-checks the manifest; a check present in-file but absent from the manifest for any gate type is a FAIL (orphan check). retro.md Step 4 pointer-resolve audit extends to manifest IDs. |
| Per-section `CHECK_LOADED` anchors add noise / rot | Anchors are HTML comments (zero render cost, ~5 tok each, ~33 total). They are generated once and audited by H1; a missing anchor on a required check fails the same as a skipped check. |
| `_gate-procedures.md` pointer dangles (graph `research-citations.md` bug) | v0.12.0 retro Step 4 resolve-every-pointer check already covers new pointers; add the manifest → anchor resolution to it. |
| Token estimate optimistic (chars/4) | Numbers are chars/4 upper bound; prose-heavy file overcounts less than code-heavy. Re-measure with the real tokenizer before committing manifest thresholds (§10.1). Directional conclusion (universal ≈ 20%, per-gate 62–77% lighter) holds. |
| Slicing churns the cached prefix | One-time re-write on ship; steady state is smaller-and-cached per gate type. The win is window headroom, which cache does not provide. |

## 8. Expected impact & measurement

- **Lever 1 alone: −3,700 tok resident on every gate, every type** — no
  manifest, no fidelity change, no behavior flag.
- **Lever 1 + Lever 2: gate resident drops to 3,076–5,103 tok** (from 13,480),
  **62–77% lighter**, deterministically, no check text altered.
- **Fewer compaction events** on long lead sessions — gates are the
  highest-resident moments (artifacts + snapshot + roles co-resident), so
  cutting gate-validation residency directly attacks saturation, the dominant
  failure mode.
- **Measure:** resident gate-validation token count per gate type before/after
  (chars/4 then real tokenizer); H1 manifest-completeness green on every gate
  type; the §5.2 slicing-bypass fixture caught; no dangling procedure pointer
  or orphan manifest ID at retro; compaction events per real sprint before/
  after.
- **Honesty:** total bytes on disk are ~unchanged (procedures moved, checks
  gated, nothing deleted). The win is keeping inapplicable checks out of the
  *resident* path per gate — v0.9.0's "move, never delete" applied to gate
  checks instead of artifacts.

## 10. Open questions

1. **Real-tokenizer re-measure before committing manifest thresholds.**
   chars/4 is an upper bound; confirm the universal ≈ 2,649 tok and the
   per-gate slices with the actual Claude tokenizer.
2. **Where does the canonical gate-type enum live?** Options: a resident
   header in `gate-validation.md` (co-located with the manifest, preferred per
   Rule 26), or `route.md` (which already assigns phase). Avoid two sources.
3. **Validate the §1 classification against the pipeline gate-type matrix.**
   Checks 16 (stub-audit), 18 (test-debt), 19 (self-reflexive Gate-2 map) were
   tagged by reading their parentheticals; confirm each against which gates
   actually run them. A mis-tag over-slices (drops a needed check → H1 catches
   it as FAIL, safe but noisy) or under-slices (carries a check that never
   fires → lost savings, not a correctness bug).
4. **RESOLVED — GREEN.** Does any step invoke a `ref` procedure expecting it
   resident? Grepped all step/role/SKILL files: every call site is an explicit
   named reference (`run X (see gate-validation.md "X")`), none relies on the
   body being pre-resident. Relocation is safe; the only work is repointing
   ~20 named references (§4 invocation audit, folded into Phase 1).
5. **Interaction with H1's existing enumerated set.** H1 currently self-tests
   Check 1c/16/17 fixtures. The manifest-completeness assertion is additive to
   that; confirm the recursion guard (`H1_DEPTH`) still short-circuits before
   the new manifest resolution to keep H1 non-recursive.
6. **Does Check 14's field-schema move with its procedure, or stay resident?**
   SKILL.md (L59/290/299/363) names Check 14 the snapshot field-schema owner —
   the most entangled of the three splits. If the schema is procedure detail,
   it moves to `_gate-procedures.md` and those four SKILL.md lines repoint (~
   more saving, more repoint surface). If the schema is a resident contract
   consumed by SKILL.md, keep it under the Check 14 mandate and move only the
   6-section update mechanics (less saving, cleaner). Decide before Phase 1
   touches Check 14; the other two procedures (auto-handoff, sub-step) have no
   such entanglement and can move first.
