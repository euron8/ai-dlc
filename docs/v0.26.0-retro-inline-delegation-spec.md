# v0.26.0 Proposal — Retro Inline-Delegation (interleaved analyst dispatch + evidence-chain preservation)

Status: **Proposed, unimplemented. Sequenced AFTER v0.25.0.** Target version:
0.26.0. Third and final lever of the delegation-closeout arc
([[v0.8.0-planning-subagent-offload-spec]] → Rule 24; Rule 28 generalized;
[[v0.25.0-lead-inline-delegation-spec]] closed the mechanical step-file gaps).
This spec closes the one step v0.25.0 deferred as out-of-scope: **retro.md**.

Retro is the largest read-heavy step (740 lines) and the lead's single biggest
inline-read site. But unlike the v0.25.0 targets, its delegable reads do NOT
factor out behind one prepended `§0` — they **interleave** with lead-owned
decisions, they are **causally ordered** (a scan that must run after an edit;
a gather that must run after a human merge gate), and they sit next to a
**provenance/evidence chain** that a careless dispatch would corrupt. This is a
design spec, not a mechanical one. It must be validated on a live retro before
being relied on.

## 1. Problem

Rule 28: reading to understand, drafting, and gathering are delegable; only
orchestration / routing / gate-decisions are inline. Retro violates this at
six sites (audit findings, Tier 3):

| Site | Lines | Inline lead work | Delegable half | Lead-owned half |
|---|---|---|---|---|
| Step 1 Context Loading | 30–36 | ingests all sprint artifacts raw | the read → digest | — (pure gather) |
| Step 3 Write Retro Doc | 93–107 | drafts analytical sections | descriptive draft | improvements + enforcement decisions |
| Step 4 Rule-file audit | 142–195 | scans 4 file-globs for 3 violation classes | detection → candidate list | disposition + rewrite authoring |
| Step 4 Dormancy + pointer scans | 197–282 | runs `gh run list` per job; multi-file pointer sweep | evidence gather | remediation choice + HARD_BLOCK verdict |
| Step 4a Close-Out Sweep | 306–433 | runs deferral conditions live; reads+matches 3 files | run checks + match tables | reclassification + mutations + locked-req disposition |
| Step 7b Next-sprint inputs | 652–681 | "Read, do not summarize" 4 sources + relatedness | gather + relatedness | theme (7c) + prompt authoring (7d) |

**Not a defect — explicitly fenced off:**
- **Step 2 Party Mode (43–91)** is already fully delegated to real subagents
  with `SKILL_INVOCATION_PROVENANCE`, a committed transcript, and a
  `transcript_path: path@<sha>` byte-match enforced by
  `validate-retro-evidence.sh`. **This spec does not touch Step 2.** It is the
  evidence core; §4 below constrains every other change to preserve it.
- Step 5 human commentary, 5b/5c gates, 6 commit/PR, 7a merge gate, 7c/7d
  theme + prompt authoring — all lead-owned (routing, gate-decisions, human
  gates, governance authoring). Untouched.

## 2. Why not one §0 (the v0.25.0 pattern does not transfer)

The mechanical instinct is "prepend one analyst dispatch that gathers
everything, then let the lead walk its decisions." **Rejected** — three
structural blockers unique to retro:

1. **Causal ordering.** Step 4's rule-file audit scans the rule files *after*
   Step 4's "apply process improvements" edits land (L191–192 even sequences
   the audit commit after the improvement commit). A single up-front gather
   would scan pre-improvement file state and miss violations the retro itself
   just introduced.
2. **A human seam mid-step.** Step 7b runs *after* the 7a merge gate — a human
   y/n. No dispatch issued before Step 5 can cover post-merge inputs.
3. **Scope hygiene.** Bundling "summarize the sprint," "detect Rule-18
   violations," and "run deferral conditions live" into one analyst prompt
   produces a muddy, unfocused scope and a large return bundle — the opposite
   of the lean, single-purpose dispatch Rule 24 models.

**Chosen design: per-phase micro-dispatches.** Each read-heavy section opens
with a scoped analyst dispatch that returns a *structured table* to a canonical
artifact and returns only `{artifact_path, summary, gaps}`; the lead resumes
in-place for disposition, authoring, and mutation. Two dispatch clusters,
because of the merge seam:

- **Dispatch A — retro evidence gather** (issued at Step 1, extended per
  section): context digest, then — after Step 4 improvements land — the
  rule-file candidate list, dormancy table, and pointer-invariant-1 sweep,
  then the Close-Out gather. These are read-only and ordered.
- **Dispatch B — next-sprint inputs** (issued at Step 7b, after the merge
  gate): epic state, carry-over candidates, open escalations, unexercised
  gates, follow-ups, related-epic candidates.

Party mode (Step 2) stays a Skill invocation between them, unchanged.

## 3. Per-site design

Each dispatch binds the `analyst` role per Rule 19 (model + role-contract Read
line) and follows Rule 24 delivery discipline (writes artifact, returns
`{artifact_path, summary, gaps}`; absent artifact = non-delivery → re-dispatch;
lead reads the artifact only when a decision needs it).

### 3.1 Step 1 — context digest

Dispatch an analyst scoped to the sprint-artifact read (stories, code reviews,
gate log, escalation log, sprint-status, context-mode protection log). It
writes a structured digest to
`_bmad-output/retro-artifacts/sprint-<N>-context.md`: planned-vs-delivered
table, rework-cycle count, `DECIDED_AUTONOMOUSLY` list, `hard_block_count` +
`hard_block_class[]` tally, per-escalation state, gate-log outcomes. The lead
consumes the digest in Step 3. **Branch creation (L18–28) stays inline** — it
is a git mutation (Rule 28a / Rule 23(c): mutations run native, never through a
subagent that discards the FS). Dispatch A is issued *after* the branch exists.

### 3.2 Step 3 — split the retro doc by disposition

- **Descriptive/analytical sections → analyst draft.** Sprint summary,
  `hard_block_count`/`class[]`, and the **Agent-findings summary** are drafted
  by the analyst from (a) the Step-1 digest and (b) the **committed party-mode
  transcript**. The agent-findings summary MUST cite the existing
  `transcript_path: path@<sha>` verbatim — the analyst summarizes the *already
  byte-cited* transcript; it never re-derives party-mode findings (doing so
  would be solo-mode-by-proxy, Rule 20). The analyst never writes a
  `SKILL_INVOCATION_PROVENANCE` block (Rule 24: analyst produces inputs, not
  validated outputs).
- **Prescriptive sections → lead, inline.** "Specific actionable
  improvements," "which improvements update CLAUDE.md / roles / steps," and the
  enforcement-layer decisions (Step 4's 5-layer mandate) stay lead-authored.
  These are pipeline self-governance — the retro's decision content — and are
  as non-delegable as gate decisions (28c-adjacent).
- **Topology-citation guard (L104–107) preserved.** Any analyst-drafted
  finding asserting infrastructure topology MUST carry the IaC `file:line`
  citation in the draft; the lead validates the citation before the finding
  lands. Agent-consensus-as-evidence stays forbidden — the analyst surfaces
  the citation, it does not substitute for it.

### 3.3 Step 4 — rule-file audit: detect delegated, dispose + author inline

The analyst produces the **candidate list**: for each of `CLAUDE.md`,
`coding-conventions.md`, `steps/*.md`, `team-roles/*.md`, every suspected
violation with `file:line`, violation class (narrative-drift / weakness /
complexity-accretion), the bare-rule-survives-without-narrative judgment as a
**recommendation**, and for accretion findings the catch/false-positive tally.
Written to `_bmad-output/retro-artifacts/sprint-<N>-rule-audit-candidates.md`.

The lead **dispositions each candidate and authors every rewrite inline.** Rule
rewriting is a judgment act expressed as text, tightly coupled to disposition;
routing the mechanical text-insertion to a dev *after* the lead has decided the
exact text is pure overhead (Rule 26 — no dispatch hop for a decision the lead
already made). Detection is the delegable read; authoring is lead governance.

**Ordering constraint:** this dispatch is issued *after* Step 4's "apply
process improvements" edits land, so the scan sees post-improvement state
(§2 blocker 1). The `## Rule File Audit` retro-doc section and the Step-5c
audit-commit sequencing are unchanged.

### 3.4 Step 4 — dormancy + pointer scans

- **Path-filter dormancy (L197–212):** analyst enumerates the `paths:`-filtered
  jobs, runs `gh run list --workflow=<wf> --branch=main --limit 30` per job
  (state-read, safe for a subagent), and returns the dormancy table (job,
  sprint-window, last non-SKIPPED SHA). The lead picks remediation (a) cite
  existing cron / (b) file Sprint N+1 task — the remediation *choice* is
  lead-owned; a dormancy finding without a remediation path is already a
  violation (L207–208).
- **Relocation-pointer scan, invariant 1 (L221–238):** the multi-file pointer
  sweep is delegable — analyst returns the pointer table (pointer, target,
  exists Y/N, anchor-resolves Y/N). The lead owns the HARD_BLOCK verdict and
  the fix.
- **Invariants 2 and 3 (L246–248, L276–278) stay as-is.** They are already
  single compact `node -e` one-liners producing tiny output. Per Rule 26 the
  one-liner *is* the minimal mechanism; wrapping it in an analyst dispatch adds
  a round-trip for no context saving. Run them via `ctx_execute` (Rule 23(c))
  so their output stays out of the resident prefix; the lead reads only the
  IN/OUT / MISSING/ORPHAN verdict lines. The verdict remains lead-owned
  (HARD_BLOCK).

### 3.5 Step 4a — Close-Out Sweep: run + match delegated, dispose inline

The heaviest interleave. Split precisely:

- **Deferral-freshness + justification-triple (L313–384):** the analyst **runs
  each deferral's live condition** (the cited test, query, or observable) and
  returns a reconciliation table: item, TRIGGER `file:line`, EFFORT-BLOCKER +
  estimate, CONDITION + live result, recommended reclassification. The lead
  **dispositions** each — the "lead is the detector" intent (L342, L361) is
  *catch-before-PVC*, not lead-hands-on-keyboard; it is satisfied as long as
  the lead decides the reclassification from the analyst's live evidence before
  the PVC. **Locked-requirement deferral disposition (L364–384) is never
  delegated** — it is a Rule 13 / Rule 12-Tier-1 HARD_BLOCK governance
  decision, lead-only.
- **Three sweep targets (L386–427):** analyst reads carry-over-backlog,
  escalations, sprint-status and returns the match table (item → satisfying
  story → recommended status). The lead dispositions. The **mutations**
  (mark `CLOSED`, verbatim cut-paste to `*-archive` per Rule 25(a), status-yaml
  drift correction) encode the lead's just-made decision on governance files;
  keep them inline with the disposition, or dispatch the mechanical
  archive-moves to `dev` if a batch is large — but the reclassification record
  is the lead's. (Recommend inline: these are small and decision-coupled.)
- **Artifact-size audit (L435–447):** analyst measures the live artifacts and
  returns sizes-vs-thresholds; the lead records the warning and the
  consolidation recommendation. Warn-only, never auto-consolidates — unchanged.

### 3.6 Step 7b — next-sprint inputs (Dispatch B)

Issued after the 7a merge gate. Analyst gathers all six input classes (epic
state, carry-over candidates, open escalations, unexercised gates, retro
follow-ups, related-epic candidates — including the relatedness analysis in
input 6) and returns the structured input bundle to
`_bmad-output/retro-artifacts/sprint-<N>-next-inputs.md`. The lead derives the
theme (7c) and authors the paste-able prompt (7d) from that bundle **plus its
own retained retro findings.**

**Step 7's design rationale is preserved.** L632–634 keeps prompt-authoring in
retro "so retro findings … are still in the lead's working context." That
rationale targets the *authoring* (7c/7d), and the lead retains exactly what it
*authored* — the Step 3 improvements and Step 4 dispositions stay resident
because the lead decided them. Only the raw *file reads* (7b) — which were never
the context-critical part — move to the analyst. The offload does not defeat
the rationale; it removes the file-reading noise from around it.

## 4. Evidence-chain preservation (the constraint Tiers 1-2 lacked)

Five invariants any implementation MUST hold. This section is the acceptance
contract.

1. **Step 2 party-mode transport is byte-unchanged.** The transcript is
   committed raw to `_bmad-output/party-mode-transcripts/sprint-<N>-retro.md`
   and cited `path@<sha>` by the lead's provenance block. No analyst produces,
   re-summarizes-into, or re-commits this file. `validate-retro-evidence.sh`
   takes the committed transcript + provenance block as inputs — neither is an
   analyst artifact — so the byte-match gate is structurally unaffected.
2. **The analyst never emits `SKILL_INVOCATION_PROVENANCE`.** Rule 24 already
   forbids it (analyst produces inputs, not validated outputs). Retro
   provenance stays the lead's, written in Step 2 / verified in Step 5c.
3. **Agent-findings summary cites, never re-derives.** The Step-3 summary the
   analyst may draft points at the existing transcript@sha; it does not
   regenerate party-mode findings from scratch (that path is solo-mode-by-proxy
   and a Rule 20 violation).
4. **Topology + trigger citations survive the hop.** Analyst-drafted findings
   carry `file:line` (topology) and TRIGGER `file:line` (deferral triple);
   the lead validates them before disposition. Consensus is not evidence.
5. **Deferral conditions are run live, not inferred.** Dispatch A's analyst
   executes each condition against the real source; a digest that *asserts* a
   condition's state without running it is non-delivery (the whole point of the
   freshness rule is a live re-check).

## 5. Enforcement (Rule 26(c) — no new machinery)

No new gate check, no new script. Two existing mechanisms cover regressions:

1. **Rule 28 lead-conduct finding** — an inline retro read outside the
   non-delegable set is already a retro finding once the dispatch points are
   the documented default.
2. **retro.md Step 4 rule-file audit** already scans `steps/*.md`. Extend its
   scope note (one line) to assert retro's own read-heavy sections carry their
   analyst dispatch — a structural invariant checked by the audit that already
   runs every retro, not a new detector. (Meta-consistent: the retro audits
   itself.)

Adding a CI gate here would be the speculative machinery Rule 26 forbids —
retro already validates itself every sprint.

## 6. Config

Reuse the existing **`planning_offload`** flag (default `on`) rather than
introduce `retro_offload`. Retro's dispatched sections are read-heavy
exploration — the exact capability the flag already governs (Rule 26: no new
config for a capability an existing flag models). Widen Rule 24's flag
description from "planning steps" to "read-heavy exploration in planning **and
retro** steps." When `off`, retro runs fully inline (pre-0.26.0 behavior).

## 7. Rollout + risk

Higher blast radius than v0.25.0 — retro is where rules get authored and the
pipeline self-improves, and the evidence chain is live. Sequence:

1. **Land v0.25.0 first.** This spec builds on its proven analyst-dispatch
   pattern; do not race them.
2. **Implement Dispatch A + B and the Step-3 split** as core-file edits to
   `retro.md` + the one-line Rule 24 flag-description widening.
3. **Validate on one full live retro** before relying on it. Acceptance: the
   five §4 invariants hold, `validate-retro-evidence.sh` and
   `validate-retro-compliance.yml` pass green, the transcript@sha byte-match is
   intact, and the lead's resident context measurably drops across the retro
   (the whole point). A retro that green-passes the evidence gate *and* shows
   the digest/candidate/table artifacts on disk is the exercise.
4. Route through the layered-rulebook discipline (Rule 27) — `retro.md` is
   core-owned, distributed by `/ai-dlc-update`.

## 8. Out of scope

- Everything v0.25.0 already owns (Tiers 1-2).
- Step 2 party-mode mechanics — fenced, never touched.
- Any change to `validate-retro-evidence.sh` / the provenance schema — the
  design's whole aim is to leave the evidence gate structurally untouched.
